# Environment Variables in Ahoy

Ahoy provides a flexible and powerful environment variable system that allows you to configure your projects dynamically and securely. This guide will walk you through everything you need to know about environment variables in Ahoy.

## Overview

Environment variables in Ahoy serve multiple crucial purposes:
- Configure project-specific settings
- Store sensitive credentials
- Customize command behavior
- Enable dynamic configuration across different environments

## Environment Variable Loading Mechanism

Ahoy loads environment variables with a specific priority and layering mechanism:

### 1. Global Environment Variables
These are standard system environment variables set in your shell or system configuration. They have the highest priority and can be set using standard shell methods:

```bash
export DB_HOST=localhost
export API_KEY=your-secret-key
```

### 2. Global `.env` File
Ahoy supports a global environment file that can be specified in your `.ahoy.yml` configuration:

```yaml
# In your .ahoy.yml
env: .env
```

The `.env` file follows standard shell variable definition syntax:

```bash
# .env file
DB_USER=root
DB_PASSWORD=mysecretpassword
LOG_LEVEL=info
```

### 3. Command-Specific Environment Files
Individual commands can also specify their own environment files that override global variables:

```yaml
commands:
  db-import:
    # This env file will override global variables for this specific command
    env: .env.db
    cmd: mysql -u$DB_USER -p$DB_PASSWORD $DB_NAME < $1
```

<Aside type="tip">
The loading order means that command-specific environment variables will override global environment variables.
</Aside>

## Environment Variable Syntax

### Standard Shell Format
Environment variables in Ahoy follow standard shell syntax:

```bash
# Simple variable
DATABASE_URL=postgres://user:pass@localhost/mydb

# Variables with spaces (use quotes)
APP_NAME="My Awesome Project"

# Referencing other variables
BASE_URL=https://example.com
API_ENDPOINT=$BASE_URL/v1/api
```

### Variable Interpolation
Ahoy supports basic shell-style variable interpolation:

```bash
# Default values
DB_HOST=${CUSTOM_HOST:-localhost}

# Conditional interpolation
LOG_LEVEL=${ENV:-development}
```

## Best Practices

### 1. Security
- Never commit sensitive information to version control
- Use `.env.example` as a template for required environment variables
- Add `.env` and `.env.*` to your `.gitignore`

### 2. Environment-Specific Configuration
Create separate environment files for different contexts:

<Tabs>
<TabItem label=".env.development">
```bash
DEBUG=true
LOG_LEVEL=verbose
DATABASE_URL=postgres://dev:password@localhost/devdb
```
</TabItem>
<TabItem label=".env.production">
```bash
DEBUG=false
LOG_LEVEL=error
DATABASE_URL=postgres://prod:securepassword@prodserver/proddb
```
</TabItem>
</Tabs>

### 3. Documenting Environment Variables
Include documentation about required environment variables in your project's README or documentation.

## Debugging and Inspection

To inspect loaded environment variables, you can use:

```bash
# This will list all environment variables recognized by Ahoy
ahoy env
```

<Aside type="caution">
Be careful when displaying environment variables, as they might contain sensitive information.
</Aside>

## Common Use Cases

### Docker Compose Integration
Environment variables are particularly useful when working with Docker Compose:

```yaml
commands:
  start:
    cmd: docker-compose up -d
    env: .env.docker
```

### Conditional Command Execution
Use environment variables to create flexible, environment-aware commands:

```yaml
commands:
  deploy:
    cmd: |
      if [ "$ENVIRONMENT" = "production" ]; then
        echo "Deploying to production..."
        # Production deployment steps
      else
        echo "Deploying to staging..."
        # Staging deployment steps
      fi
```

## Advanced Configuration

For complex scenarios, you can combine environment files, system variables, and inline environment definitions:

```yaml
commands:
  complex-command:
    env: .env.custom  # Load a specific env file
    cmd: |
      # Use variables from .env.custom, overridden by system env
      echo "User: $USER, Database: $DB_NAME"
```

## Troubleshooting

- **Variable Not Working?**
  - Check variable spelling
  - Verify case sensitivity
  - Confirm the variable is in the correct scope
- **Security Concerns?**
  - Review who has access to your environment files
  - Rotate credentials regularly
  - Use secret management tools for sensitive data
