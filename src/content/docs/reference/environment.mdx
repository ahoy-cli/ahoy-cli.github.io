# Environment Variables Reference

This reference provides a comprehensive technical guide to environment variables in Ahoy, including implementation details, supported formats, precedence rules, and advanced usage patterns.

## Technical Specification

### Implementation Overview

Ahoy's environment variable system is implemented in the core Go code (`ahoy.go`). The system processes environment files line by line, supports nesting and overrides, and injects variables into command execution contexts.

Key implementation facts:
- Environment variables are read and parsed using the `getEnvironmentVars()` function
- Variables are injected into each command's environment via the `command.Env` property
- All environment files are relative to the location of the `.ahoy.yml` file
- Variable resolution follows a precise override chain (system → global → command-specific)

### Environment File Locations and Resolution

#### Global Environment File

Specified at the top level of your `.ahoy.yml`:

```yaml
ahoyapi: v2
env: .env  # Path is relative to the location of .ahoy.yml

commands:
  # All commands can access variables from .env
```

#### Command-Specific Environment File

Specified within individual commands:

```yaml
commands:
  deploy:
    usage: Deploy application
    env: .env.deploy  # Path is relative to the location of .ahoy.yml
    cmd: ./deploy.sh
```

### File Path Resolution Logic

Environment file paths are always relative to the directory containing the `.ahoy.yml` file, not the current working directory. This ensures consistent behavior regardless of where the command is executed from.

From the implementation in `ahoy.go`:

```go
if config.Env != "" {
    globalEnvFile := filepath.Join(AhoyConf.srcDir, config.Env)
    envVars = append(envVars, getEnvironmentVars(globalEnvFile)...)
}

// For command-specific env files
if cmd.Env != "" {
    cmdEnvFile := filepath.Join(AhoyConf.srcDir, cmd.Env)
    envVars = append(envVars, getEnvironmentVars(cmdEnvFile)...)
}
```

## Environment File Format Specification

Ahoy uses standard shell-style environment files with the following technical specifications:

### Syntax Rules

1. **Line Format**: Each non-empty, non-comment line must define a single variable
2. **Variable Names**: Can contain letters, numbers, and underscores; conventionally uppercase
3. **Assignment**: Uses the `=` character with no spaces around it
4. **Comments**: Lines starting with `#` are ignored
5. **Inline Comments**: Anything after `#` on a line is ignored
6. **Whitespace**: Leading/trailing whitespace is trimmed
7. **Quotes**: Optional for values, required for values with spaces
8. **Export Keyword**: Optional `export` prefix is accepted but has no effect

### Format Specification

```
[export] NAME=VALUE[#comment]
```

Where:
- `[export]` is optional and ignored by Ahoy
- `NAME` is the variable name
- `VALUE` is the variable value
- `[#comment]` is an optional inline comment

### Examples with Technical Details

```bash
# Simple variable (no quotes needed for simple values)
USERNAME=admin

# Variable with spaces (quotes required for spaces)
FULL_NAME="John Doe"

# Empty variable (valid, sets to empty string)
CACHE_DIR=

# Comments are ignored (entire line)
# This line is completely ignored

# Inline comments are ignored (partial line)
API_KEY=abc123  # This comment is ignored by the parser

# Multi-line variables (newlines preserved in quoted values)
SSH_KEY="-----BEGIN RSA PRIVATE KEY-----
MIIEpQIBAAKCAQEA14+bB+QIDAQAB
...
-----END RSA PRIVATE KEY-----"

# Export syntax (recognized but has no special effect in Ahoy)
export DATABASE_URL=postgres://user:pass@localhost/mydb
```

### Parser Implementation Details

The environment variable parser in Ahoy:
1. Reads the file line by line
2. Trims whitespace from each line
3. Skips empty lines and lines starting with `#`
4. Doesn't handle variable interpolation within the file itself
5. Doesn't support backslash escapes or shell-style substitutions

From `ahoy.go`:
```go
func getEnvironmentVars(envFile string) []string {
    var envVars []string
    env, err := os.ReadFile(envFile)
    if err != nil {
        logger("fatal", "Invalid env file: "+envFile)
        return nil
    }
    lines := strings.Split(string(env), "\n")
    for _, line := range lines {
        line = strings.TrimSpace(line)
        // Ignore empty lines and comments (lines starting with '#').
        if line == "" || strings.HasPrefix(line, "#") {
            continue
        }
        envVars = append(envVars, line)
    }
    return envVars
}
```

## Variable Types and Format Specifications

All environment variables in Ahoy are technically strings, but they can represent different types of data through conventional formats:

### Strings

```bash
# Plain string
APP_NAME=myapp

# String with spaces (requires quotes)
APP_DESCRIPTION="My Awesome Application"

# String with special characters
MESSAGE="Hello, world!"
```

### Numbers

```bash
# Integer
PORT=8080

# Floating point
TIMEOUT=15.5
```

### Booleans

```bash
# Boolean values (interpreted as strings)
DEBUG=true
CACHE_ENABLED=false
```

### Paths

```bash
# Absolute path
LOG_DIR=/var/log/myapp

# Relative path
CONFIG_FILE=./config.json

# Path with environment variable
PLUGIN_DIR=${HOME}/plugins
```

### URLs and Connection Strings

```bash
# URL
API_ENDPOINT=https://api.example.com

# Database connection string
DATABASE_URL=postgres://user:password@localhost:5432/mydb

# Complex connection string with parameters
REDIS_URL=redis://:authpassword@redis.example.com:6379/0?timeout=30s
```

## Structured Data Handling

While environment variables are inherently string-based, Ahoy commands often need to work with structured data formats. Here are techniques for handling various complex data types in Ahoy environment files:

### JSON Data

JSON data can be stored in environment variables but requires proper escaping of quotes:

```bash
# Simple JSON object
CONFIG_JSON="{\"debug\":true,\"timeout\":30,\"retries\":3}"

# To use in commands:
# echo $CONFIG_JSON | jq '.debug'
```

When working with JSON data in commands:

```yaml
commands:
  process-config:
    env: .env.json
    cmd: |
      echo "Processing config with timeout: $(echo $CONFIG_JSON | jq -r '.timeout')"
      # Further processing with jq
```

### YAML Data

For YAML data, you can store it as a multi-line string and process it in commands:

```bash
# Multi-line YAML stored as a string
CONFIG_YAML="
server:
  port: 8080
  host: localhost
logging:
  level: info
  file: /var/log/app.log
"
```

Usage in commands:

```yaml
commands:
  yaml-process:
    env: .env.yaml
    cmd: |
      echo "$CONFIG_YAML" > temp_config.yml
      yq eval '.server.port' temp_config.yml
      rm temp_config.yml
```

### Base64 Encoded Data

For binary data or complex structures, Base64 encoding provides a safe transport mechanism:

```bash
# Certificate stored as Base64
SSL_CERT="LS0tLS1CRUdJTiBDRVJUSUZJQ0FURS0tLS0tCk1JSUVwRENDQTR5Z0F3SUJBZ0lKQVBKaW..."

# Binary configuration
BINARY_CONFIG="SGVsbG8gQWhveSBDb25maWd1cmF0aW9uIQ=="
```

In commands:

```yaml
commands:
  use-cert:
    env: .env.certs
    cmd: |
      echo "$SSL_CERT" | base64 -d > temp.cert
      # Use certificate
      rm temp.cert
```

### Environment Variables as Configuration Files

For complex configurations, you can use environment variables to dynamically generate config files:

```bash
# Template contents for a config file
NGINX_CONF="
server {
    listen 80;
    server_name ${DOMAIN_NAME};
    
    location / {
        proxy_pass ${BACKEND_URL};
    }
}
"

# Variables used in the template
DOMAIN_NAME=example.com
BACKEND_URL=http://localhost:8080
```

In your command:

```yaml
commands:
  deploy-nginx:
    env: .env.nginx
    cmd: |
      # Perform variable substitution and write config
      eval "echo \"$NGINX_CONF\"" > nginx.conf
      # Use the generated config file
```

## Variable Precedence and Implementation

### Precedence Rules

Ahoy uses a clearly defined precedence order when resolving environment variables. From highest precedence (overrides all others) to lowest:

1. Command-line arguments (passed directly to the command)
2. Command-specific environment file variables
3. Global environment file variables
4. Environment variables from the shell where Ahoy is running
5. Default values specified in scripts

This means variables defined in a command's environment file will override those with the same name in the global environment file.

### Implementation Details from ahoy.go

The precedence is implemented through the order of append operations in the source code:

```go
// First get environment variables from the OS
envVars := os.Environ()

// Then append global environment variables
if config.Env != "" {
    globalEnvFile := filepath.Join(AhoyConf.srcDir, config.Env)
    envVars = append(envVars, getEnvironmentVars(globalEnvFile)...)
}

// Finally append command-specific environment variables (highest precedence)
if cmd.Env != "" {
    cmdEnvFile := filepath.Join(AhoyConf.srcDir, cmd.Env)
    envVars = append(envVars, getEnvironmentVars(cmdEnvFile)...)
}
```

Since later definitions with the same name override earlier ones, this implements the precedence chain.

### Variable Merging Behavior

When merging environment variables from multiple sources:

1. Variables are processed in order of precedence
2. If a variable already exists, its value is replaced by the new value
3. No partial merging occurs for complex values - entire values are replaced

<Aside type="caution">
Variables passed to commands via the shell's environment may be overridden by identically named variables in your `.env` files. This is by design and allows predictable environment configuration.
</Aside>

## Command Execution Context

### Environment Variable Injection

When Ahoy executes a command, it creates a new process with a carefully constructed environment that includes all resolved variables. The technical implementation:

```go
cmd := exec.Command(args[0], args[1:]...)
cmd.Dir = AhoyConf.srcDir
cmd.Stdout = os.Stdout
cmd.Stderr = os.Stderr
cmd.Stdin = os.Stdin
cmd.Env = envVars  // All environment variables are injected here
if err := cmd.Run(); err != nil {
    // Error handling
}
```

### Runtime Variable Manipulation

Commands can modify their own environment variables at runtime, but these changes:

1. Only affect the current command execution
2. Are not persisted back to the environment files
3. Are not propagated to other commands

For example:

```yaml
commands:
  dynamic-env:
    cmd: |
      # Set a new variable at runtime
      export RUNTIME_VAR="Generated at $(date)"
      echo "Using $RUNTIME_VAR"
      # This variable will not be available to other commands
```

## Error Handling and Edge Cases

### Missing Environment Files

When a specified environment file is missing:

```go
env, err := os.ReadFile(envFile)
if err != nil {
    logger("fatal", "Invalid env file: "+envFile)
    return nil
}
```

Ahoy terminates with a fatal error if it cannot find or read a specified environment file. This is a deliberate design choice to fail fast rather than continue with potentially incomplete configuration.

### Variable Syntax Errors

Lines in `.env` files that don't conform to the expected format are processed as follows:

1. Lines without an `=` character are added to the environment verbatim
2. This may cause unexpected behavior in the shell
3. No syntax validation is performed beyond basic trimming and comment handling

Example of potentially problematic syntax:

```bash
# This will be added as-is and may cause shell errors
INVALID VARIABLE SYNTAX

# This will be added as NAME WITH SPACES=value
NAME WITH SPACES=value
```

### Circular References

Ahoy doesn't resolve variable references within environment files. If you have:

```bash
BASE_URL=http://example.com
API_URL=${BASE_URL}/api  # This will NOT be resolved
```

The literal value `${BASE_URL}/api` will be passed to the command. Resolution depends on the shell or script handling:

```yaml
commands:
  show-urls:
    env: .env.urls
    cmd: |
      # In bash, this works because bash performs the variable substitution
      echo $API_URL  # Outputs: http://example.com/api
      
      # In Node.js, this would not be automatically resolved
      # process.env.API_URL would contain "${BASE_URL}/api"
```

### Character Encoding Issues

Environment files should be UTF-8 encoded. Other encodings may cause:

1. Non-ASCII characters to be improperly interpreted
2. Command failures with encoding-related errors
3. Unexpected behavior when passing values to processes

## Technical Troubleshooting

### Diagnostic Tools

When troubleshooting environment variable issues, use these techniques:

```yaml
commands:
  debug-env:
    env: .env.debug
    cmd: |
      # Print all environment variables
      env | sort
      
      # Check specific variables
      echo "DB_HOST=$DB_HOST"
      echo "API_KEY=${API_KEY:-not set}"
```

### Common Issues and Solutions

#### Variable Not Available to Command

**Problem**: A variable defined in an environment file isn't accessible in the command.

**Debugging Steps**:

1. Verify the environment file path is correct relative to `.ahoy.yml`
2. Check for syntax errors in the environment file
3. Ensure the variable isn't being overridden by another environment source
4. Add a debug command to print all environment variables

```yaml
commands:
  debug:
    env: .env.debug
    cmd: env | grep MISSING_VARIABLE
```

#### Variable Value Unexpected

**Problem**: A variable has an unexpected value.

**Solution**: Check for precedence issues:

```yaml
commands:
  check-precedence:
    cmd: |
      echo "From shell: $VARIABLE"
      
      # Add a temporary environment file with the variable
      echo "VARIABLE=from-file" > temp.env
      
      # Run a command with the file
      ahoy --env temp.env echo "From file: $VARIABLE"
      
      rm temp.env
```

#### Special Characters in Variables

**Problem**: Special characters in variables causing command failures.

**Solution**: Use proper quoting:

```yaml
commands:
  special-chars:
    env: .env.special
    cmd: |
      # Echo with quotes to preserve special characters
      echo "$SPECIAL_CHARS"
      
      # For command arguments that need special character handling
      grep -F "$SEARCH_PATTERN" filename
```

#### Multi-line Variables

**Problem**: Multi-line variables being truncated or improperly formatted.

**Solution**: Use proper quoting and temporary files:

```yaml
commands:
  multiline:
    env: .env.multiline
    cmd: |
      # Write to a temporary file to preserve formatting
      echo "$MULTI_LINE_VAR" > temp.txt
      cat temp.txt
      rm temp.txt
```

## Performance Considerations

### File Size Impact

The environment variable system reads files completely into memory:

```go
env, err := os.ReadFile(envFile)
```

Very large environment files (multiple megabytes) may impact:
1. Memory usage
2. Command startup time
3. Overall system performance

**Best practice**: Keep environment files under 100KB for optimal performance.

### Environment File Organization

For complex projects with many variables, consider:

1. **Separate by Environment**: Create different files for different deployment targets:

```
project/
├── .ahoy.yml
├── .env                  # Global, shared variables
├── .env.development      # Development-specific
├── .env.staging          # Staging-specific
├── .env.production       # Production-specific
```

2. **Separate by Function**: Group variables by their functional area:

```
project/
├── .ahoy.yml
├── .env                  # Global, shared variables
├── .env.database         # Database connection variables
├── .env.apis             # API keys and endpoints
├── .env.services         # Service configuration
```

3. **Command-Specific Organization**: Create dedicated environment files for specific commands:

```yaml
commands:
  deploy-prod:
    usage: Deploy to production
    env: .env.deploy.production
    cmd: ./deploy.sh
    
  deploy-staging:
    usage: Deploy to staging
    env: .env.deploy.staging
    cmd: ./deploy.sh
```

4. **Include Version Control Considerations**:

```
project/
├── .ahoy.yml
├── .env.example           # Template with placeholders (committed)
├── .env                   # Local env vars (not committed)
├── .env.ci                # CI environment (committed)
├── .gitignore             # Contains ".env" pattern
```

### Implementation Technical Details

When organizing files, remember these technical implementation facts:

1. Ahoy resolves file paths relative to the `.ahoy.yml` file location
2. No automatic directory traversal or parent directory lookup occurs
3. Files are processed in their entirety, not incrementally or partially
4. No automatic file extension recognition - filenames must be exact

## Integration with Other Tools

Ahoy's environment variable system is designed to interoperate with other common development tools and practices.

### Docker Integration

Environment variables can be passed to Docker containers:

```yaml
commands:
  docker-run:
    env: .env.docker
    cmd: |
      # Pass all environment variables to Docker
      docker run --rm $(env | grep -E '^(DB_|API_)' | sed 's/^/-e /') image:tag
      
      # Or, pass specific variables
      docker run --rm -e DB_HOST -e DB_USER -e DB_PASS image:tag
```

### CI/CD Systems

For continuous integration environments:

```yaml
commands:
  ci-build:
    env: .env.ci
    cmd: |
      # Travis CI
      if [ "$TRAVIS" = "true" ]; then
        echo "Running in Travis CI"
      fi
      
      # GitHub Actions
      if [ -n "$GITHUB_ACTIONS" ]; then
        echo "Running in GitHub Actions"
      fi
      
      # Execute the build command
      ./build.sh
```

### Credential Management Systems

Integration with credential storage tools:

```yaml
commands:
  aws-deploy:
    cmd: |
      # Load AWS credentials from credential helper
      export AWS_ACCESS_KEY_ID=$(aws configure get aws.access_key_id)
      export AWS_SECRET_ACCESS_KEY=$(aws configure get aws.secret_access_key)
      
      # Use credentials
      aws s3 sync ./dist s3://my-bucket/
```

### Local Development Tools

Working with local development tools:

```yaml
commands:
  init:
    cmd: |
      # Check for required tools
      if ! command -v docker > /dev/null; then
        echo "Docker not found"
        exit 1
      fi
      
      # Generate local environment file if not exists
      if [ ! -f .env ]; then
        cp .env.example .env
        echo "Created .env from template"
      fi
```

### Technical Implementation Notes

The environment variable system in Ahoy:

1. Is implemented as simple string passing, not as an API or protocol
2. Doesn't implement secure variable storage or encryption
3. Relies on the underlying shell or script for variable resolution
4. Can be extended by writing wrapper scripts that manage credentials or configurations
